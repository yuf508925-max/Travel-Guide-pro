## 顶部导航条加音量键（ChatView.vue）

- 需求来源：用户分享的 WorkBuddy page 链接（https://workbuddy.link/p/eBzoKJQUl5fXu98mWgo3Cx），
  里面是之前某次对话的"音量按钮怎么写"方案：滑块放 `chat-user-box` 内、退出按钮左边，
  `const volume = ref(80)`，CSS 用 `accent-color: #fffdf8` 上色（一行搞定，不用手写伪元素）。
  分享页的真实内容取法：页面是 SPA，直接 curl 拿不到正文；要从 HTML 里的
  `window.__PUBLISH_BOOTSTRAP__.artifact.url` 拼出 `conversation-data.json` 再解析 messages。
- 实现（ChatView.vue）：
  - 模板：`chat-user-box` 里加 `.volume-box` = 小喇叭按钮（inline SVG，静音时换成叉号）+ `<input type="range" v-model.number="volume">`；
    `.chat-page` 顶部加隐藏 `<audio ref="audioRef" :src="BGM_SRC" loop preload="auto" autoplay />`
  - 脚本：`volume = ref(80)`、`muted = ref(false)`、`applyVolume()` 把 `muted ? 0 : volume/100` 写进 audio；
    `watch([volume, muted], applyVolume)`；喇叭按钮 `toggleMute()`
  - 自动播放会被浏览器拦截 → `onMounted` 先 `play().catch(()=>{})`，再挂一次性 `pointerdown` 监听在首次交互时重试
  - 音源用了 public 下一直没被引用的 `Travelers' encore - Andrew Prahlow.mp3`（BGM）
- 验证：vue-tsc 零报错、vite build 通过；CDP 冒烟 → 滑块 80/宽 90px、audio.volume 0.8，
  拖到 30 → 0.3，静音 → 0 且加 `--muted` class，取消静音 → 恢复 0.3，控制台 0 异常

## 环境坑：node_modules 被 pnpm 化，npm install 在 Windows 上报 EPERM

- 现象：`npx vue-tsc` / `vite` 全部 `MODULE_NOT_FOUND`，node_modules 只剩 122 个目录但 `.pnpm` 里有 218 个包
  （顶层 vue / vite / typescript / pixi 的软链接全没了），项目根多了 `pnpm-lock.yaml`
- `npm install` 报错 `EPERM: syscall symlink`（npm 用真符号链接，Windows 无管理员权限建不了；
  即使 dangerouslyDisableSandbox 也一样失败）
- **解法：用 `pnpm install`**（pnpm 在 Windows 上用 junction 而非 symlink，不需要管理员权限），6 秒装完 216 个包
- 结论：这个项目现在是 pnpm 管理的，后续装依赖一律用 pnpm，别用 npm

## 排查：填了 Key 却 401（真凶是 dotenv 不覆盖系统环境变量）

- 现象：用户在 `server/.env` 写入真实 Key，仍报 `401 Incorrect API key`
- **根因：Windows 系统环境变量里本来就有一个失效的 `DEEPSEEK_API_KEY`，
  而 `load_dotenv()` 默认不覆盖已存在的环境变量 → 程序一直在用系统里那个旧 Key**
- 修法：`load_dotenv(path, override=True)`（写在 `server/config.py`）
- 排查手法（可复用）：
  1. 打印 `config.X` 的实际值（长度/首尾）与 .env 文件内容比对 → 发现两者不同
  2. `os.environ` 里是否已存在同名变量 → 确认被系统变量抢占
  3. 用 `AsyncOpenAI(base_url=...).models.list()` 探测候选端点，看哪个能过鉴权
- 用户实际用的是**阿里云百炼（DashScope）兼容模式**，不是 DeepSeek 官方：
  `DEEPSEEK_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1`，模型 `deepseek-v4-pro`
  （该端点共 262 个模型，确实含 deepseek-v4-pro；国际版 dashscope-intl 用的是另一套 Key，会 401）
- 端到端已验证：5173 → Vite 代理 → 8000 → 百炼 → SSE 回流正常（芙芙能正常作答）
- 环境坑：本机有 `HTTP_PROXY=http://127.0.0.1:55047`，**curl 打 localhost 必须加 `--noproxy '*'`**，
  否则会被沙箱代理拦掉，报 “upstream connect failed”
- 环境坑：Bash 工具里用 `cmd &` 起的进程会随该次调用结束被回收；
  要长期运行的服务必须用 `run_in_background: true` 启动

## 修复「开头干等才出字」（推理模型 + 逐字队列，为 TTS 铺路）

- 症状：发消息后要空等约 6 秒才出现第一个字
- 原因：`deepseek-v4-pro` 是**推理模型**，流式时先吐 `delta.reasoning_content`（思考过程，实测 338 字），
  约 6.4 秒后才开始吐 `delta.content`；旧代码只取 content，思考期间前端一片空白
- 实测数据（一次「成都3天怎么玩」）：首字延迟 6.4s、正文 2220 字、293 个片段、
  平均每段 7.6 字、间隔 0.11s（≈70 字/秒，肉眼是成块刷不是打字机）、总耗时 33.6s
- 改动：
  - `providers/deepseek.py`：`stream_chat()` 改为 yield `(kind, text)` 三元组类型 ——
    `'status'`（开局先发一帧 thinking 状态）/ `'thinking'` / `'text'`
  - `routers/chat.py`：SSE 帧带 `{"type": kind, "text": ...}`
  - `useChatStream.ts`：新增 `isThinking`、`thinkingText`；**正文不再直接追加，
    而是进字符队列逐字放出**（`TICK_MS=50`、`CHARS_PER_TICK=1` ≈ 20 字/秒，
    积压 >60 字自动加速）；`useChatStream({ onChar })` 钩子留给 TTS —— 接 TTS 时在
    onChar 里触发朗读即可做到「说一个字显示一个字」；收尾要 await 队列排空再解锁输入框
  - `MessageList.vue`：新增 `isThinking` prop → 显示「芙芙正在思考」气泡 + 三点跳动动画
  - `ChatView.vue`：把 `isThinking` 传给 MessageList
- ⚠️ **用户在同时编辑源文件**：我改完 `providers/deepseek.py` 后，用户自己的版本（把人设
  改成「原神角色芙宁娜」）在 13:27 覆盖了我的改动，导致 `too many values to unpack`。
  教训：改这个文件前先 Read 最新版，改完最好核一遍；重要改动后提醒用户别用编辑器旧内容覆盖
- ⚠️ uvicorn `--reload` 在这个环境里不总是生效，改完后端要**手动重启**（taskkill 掉占 8000 的进程再起）
- TTS 前的配套建议：SYSTEM_PROMPT 里的长度限制要压到 150~200 字（现在用户版本是 300 字），
  否则 20 字/秒逐字显示 + 朗读会非常久
